# Terraform module for Amazon Redshift clusters

Creates a provisioned Amazon Redshift cluster with its subnet group, parameter group, security group and IAM role, and CloudWatch alarms that notify two Amazon SNS topics. Optional settings cover multi-node and Multi-AZ clusters, your own KMS key, audit logging to CloudWatch Logs or Amazon S3, snapshot schedules, workload management and other parameters, permissions for `COPY` and `UNLOAD`, and restoring from a snapshot.

The defaults are the settings most production data warehouses should have. A cluster created with only the required inputs is encrypted, keeps its master password in AWS Secrets Manager instead of in Terraform state, accepts only connections that use TLS, cannot be reached over the network until you allow a source, has no public address, sends its Amazon S3 traffic through the VPC, and takes a final snapshot when it is deleted.

## What it configures

| Setting | Default | Input |
|---|---|---|
| Encryption at rest | Always on, with a key AWS owns | `kms_key_id` |
| Master password | Generated by Amazon Redshift and kept in Secrets Manager | `master_password` |
| Connections | TLS required (`require_ssl`) | `parameter_group` |
| Network access | None: no client can connect | `security_group_ingress` |
| Outbound connections | HTTPS to Amazon S3 in the Region only | `allow_s3_egress`, `security_group_egress` |
| Public IP address | None | `publicly_accessible` |
| Enhanced VPC routing | On | `enhanced_vpc_routing` |
| IAM role | Created, with no permissions | `iam_role` |
| Nodes | One, moved to another Availability Zone if its zone fails | `number_of_nodes`, `availability_zone_relocation`, `multi_az` |
| Automated snapshots | Kept for 7 days | `backup` |
| Final snapshot on delete | Taken and kept | `skip_final_snapshot` |
| Engine upgrades | Applied by AWS in the maintenance window | `maintenance` |
| Audit logging | Off | `logging` |
| Alarms | Health, CPU and disk space, to two SNS topics | `alarms` |

## Usage

```hcl
module "warehouse" {
  source  = "AutomateTheCloud/redshift/aws"
  version = "~> 1.0"

  details = {
    scope       = "Automate the Cloud"
    purpose     = "Analytics"
    environment = "Production"
  }

  name       = "analytics"
  node_type  = "ra3.large"
  vpc_id     = "vpc-0123456789abcdef0"
  subnet_ids = ["subnet-0123456789abcdef0", "subnet-0fedcba9876543210"]

  security_group_ingress = {
    bi = { security_group_id = "sg-0123456789abcdef0", description = "Reporting servers" }
  }
}
```

`details`, `name`, `node_type`, `vpc_id` and `subnet_ids` are the only required inputs. `details` sets the `Scope`, `Purpose` and `Environment` tags on every resource.

Clients connect to `module.warehouse.metadata.redshift_cluster.dns_name` on `metadata.redshift_cluster.port`, database `dev` unless you set `database_name`, as `awsuser` unless you set `master_username`. The master password is in the Secrets Manager secret whose ARN is `module.warehouse.metadata.redshift_cluster.master_password_secret_arn`.

The module uses your default `aws` provider and creates everything in that provider's Region. To create the cluster somewhere else without configuring another provider, set `region`:

```hcl
module "warehouse_us_west_2" {
  source  = "AutomateTheCloud/redshift/aws"
  version = "~> 1.0"

  region     = "us-west-2"
  details    = { scope = "Automate the Cloud", purpose = "Analytics", environment = "Production" }
  name       = "analytics"
  node_type  = "ra3.large"
  vpc_id     = "vpc-0abcdef0123456789"
  subnet_ids = ["subnet-0abcdef0123456789", "subnet-0123456789abcdef1"]
}
```

The VPC, the subnets and any KMS key must be in that Region too. The cluster's IAM role is global; its name starts with the cluster's name and its description says which Region it is for.

To use a provider configured for another account, pass it explicitly with `providers = { aws = aws.other_account }`.

## The `details` input

Most modules ask only for what the resource itself needs. This one also requires `details`: three names that say what the cluster belongs to, what it is for, and which environment it is in. Every Automate the Cloud module takes the same input, and requiring it is deliberate.

```hcl
details = {
  scope       = "Automate the Cloud" # what it belongs to: an organization, team or project
  purpose     = "Analytics"          # what it is for
  environment = "Production"         # which environment
}
```

**Every resource can be traced.** The three names become the `Scope`, `Purpose` and `Environment` tags on every resource the module creates. Months later, anyone looking at a cluster in the AWS console, or at a line on the bill, can see who it belongs to and why it exists. With cost allocation tags turned on in AWS Billing, the same tags split your bill by project and environment. Because the input is required and checked, no resource can be created without them.

**One definition for a whole stack.** Write `details` once and pass the same value to every module, so the data warehouse, its network, its encryption key and everything else are tagged alike. Tags you want everywhere, such as a cost center or the Terraform workspace, go in `additional_tags`:

```hcl
locals {
  details = {
    scope           = "Automate the Cloud"
    purpose         = "Analytics"
    environment     = "Production"
    additional_tags = { CostCenter = "1234", IaC = "true" }
  }
}

module "warehouse" {
  source  = "AutomateTheCloud/redshift/aws"
  version = "~> 1.0"

  details    = local.details
  name       = "analytics"
  node_type  = "ra3.large"
  vpc_id     = "vpc-0123456789abcdef0"
  subnet_ids = ["subnet-0123456789abcdef0", "subnet-0fedcba9876543210"]
}
```

**Consistent names.** The module turns each name into two short forms other resources can be named with: `abbr`, lowercase with words joined by underscores (`Data Warehouse` becomes `data_warehouse`), and `machine`, lowercase letters and numbers only (`datawarehouse`), for resources that allow no underscores. It also works out a short form of the Region, such as `use1` for `us-east-1`. Every module derives these the same way, so names stay consistent across a stack. To choose your own short forms, set `scope_abbr`, `purpose_abbr` or `environment_abbr`, for example `environment_abbr = "prd"`.

**One output to reach everything.** All of it comes back in the `metadata` output, along with everything the module created, so a configuration needs only one reference: `module.warehouse.metadata.redshift_cluster.dns_name` for the address clients connect to, or `module.warehouse.metadata.aws.region.abbr` for the Region's short form.

## Things to know

### Deleting a cluster

Amazon Redshift has no deletion protection: `terraform destroy`, or a change that replaces the cluster, deletes it. Deleting the cluster first takes a final snapshot named `<name>-final-<8 hex digits>`, unless `skip_final_snapshot` is `true`. The final snapshot, and any manual snapshot, is kept and billed until you delete it. To start a new cluster from it, pass its name in `snapshot_identifier`. Automated snapshots are deleted with the cluster.

### Settings fixed at creation

Changing `name` replaces the cluster: Terraform deletes it, taking the final snapshot, and creates an empty one. So does moving it to subnets in another VPC. Read the plan before you apply: a line saying the cluster `must be replaced` means this.

AWS refuses to change the cluster's KMS key, `kms_key_id`, once the cluster exists, including setting one on a cluster created without it: the plan shows an update, and the apply fails with `InvalidParameterCombination`. To move the data to another key, restore a snapshot into a new cluster: give the new cluster another `name`, the snapshot in `snapshot_identifier`, and the key in `kms_key_id`.

Some settings are used only when the cluster is created, and changing them later does nothing: `database_name`, `master_username` and `snapshot_identifier`. Create databases and users with SQL after that.

Most other settings change in place. Changing `node_type` or `number_of_nodes` resizes the cluster, which can take a long time on a large cluster. After a change of `port`, the first plan shows only `metadata` changing, because the provider saves the cluster before AWS reports the new endpoint; applying that plan changes no resources.

### The master password

By default Amazon Redshift generates the master password and keeps it in a Secrets Manager secret that it manages, so it never appears in Terraform state or plans. Read it with `aws secretsmanager get-secret-value --secret-id <secret ARN>`, or let applications read it with an IAM policy that allows `secretsmanager:GetSecretValue` on that secret (and `kms:Decrypt` on `master_password_secret_kms_key_id`, if you set one). Secrets Manager bills for each secret.

If the password must come from somewhere else, pass it in `master_password`. Terraform then stores it in plain text in its state, so protect the state. Switching to `master_password` updates the cluster in place, and Amazon Redshift deletes its secret; the first plan afterwards shows only `metadata` changing, and applying it changes no resources.

Switching back, by removing `master_password`, fails: the AWS provider sends the removed password as an empty one, and AWS refuses it (`MasterUserPassword must be provided and must not be blank`). Make the change outside Terraform, then let Terraform read the cluster again, which forgets the old password:

```shell
aws redshift modify-cluster --cluster-identifier <name> --manage-master-password
terraform state rm module.warehouse.aws_redshift_cluster.this
terraform import module.warehouse.aws_redshift_cluster.this <name>
terraform apply
```

Add `--master-password-secret-kms-key-id <key ARN>` to the first command if you set `master_password_secret_kms_key_id`. The last apply changes nothing in AWS: it saves what the import did not read.

For applications, temporary credentials avoid passwords altogether: `aws redshift get-cluster-credentials-with-iam` returns a short-lived user name and password for the caller's IAM identity. The [Amazon Redshift Data API](https://docs.aws.amazon.com/redshift/latest/mgmt/data-api.html) runs SQL over HTTPS with IAM credentials and needs no network access to the cluster.

### Network access

The module's security group allows the cluster's port, over TCP, from the sources in `security_group_ingress`, and nothing else. Its only outbound rule allows HTTPS to Amazon S3 in the cluster's Region, through the Region's S3 prefix list. With `enhanced_vpc_routing`, on by default, `COPY`, `UNLOAD` and Redshift Spectrum reach S3 through the VPC, so the VPC also needs a route to S3: an S3 gateway endpoint on the subnets' route tables, or a NAT gateway. Add `security_group_egress` for anything else the cluster connects to, such as an RDS database for federated queries. Without enhanced VPC routing, that traffic leaves through the internet, outside the VPC's controls, and AWS gives each node a public IP address for it.

To let another resource in, use its security group as the source, so the rule follows the resource as its addresses change. Use the module's group, `metadata.security_group.id`, as the destination in that resource's own outbound rules.

Use private subnets in `subnet_ids`. `publicly_accessible` gives the cluster a public address, which, in subnets with a route to an internet gateway, lets anyone on the internet whom `security_group_ingress` allows reach it. Prefer a private connection, such as a VPN, AWS Systems Manager port forwarding through an instance in the VPC, or the Data API.

### TLS

The module's parameter group sets `require_ssl` to `true`, so the cluster refuses connections that do not use TLS. Most clients do this already; with `psql`, add `sslmode=require`. Set `parameter_group.parameters.require_ssl = "false"` only for a client that cannot.

The parameter group is named `<name>-<family>`, such as `analytics-redshift-2-0`. A new `parameter_group.family` creates a new group, moves the cluster to it, and then deletes the old one. Some parameters take effect only after the cluster restarts. Removing a parameter from `parameter_group.parameters` does not reset it in AWS, and every plan then tries to remove it again: set it to the family's default value instead.

### Permissions for COPY and UNLOAD

The module creates an IAM role for the cluster and makes it the cluster's default role, so SQL can name it as `IAM_ROLE default`:

```sql
COPY sales FROM 's3://my-data-bucket/sales/' IAM_ROLE default FORMAT AS PARQUET;
```

The role has no permissions until you give it some in `iam_role`. Grant only what the cluster needs: the [complete example](https://github.com/AutomateTheCloud/terraform-aws-redshift/tree/main/examples/complete) gives read access to one bucket with `iam_role.source_policy_documents`. `iam_role.managed_policy_arns` attaches managed policies; AWS managed policies such as `AmazonS3ReadOnlyAccess` grant far more, here every bucket in the account. Roles that you manage yourself can be associated with the cluster through `iam_role.additional_role_arns`.

### Audit logging

`logging.destination` turns on audit logging of connections (`connectionlog`), changes to users (`userlog`) and every query (`useractivitylog`). With `cloudwatch`, the module creates each log group, `/aws/redshift/cluster/<name>/<log>`, before logging starts, so its retention applies from the start. With `s3`, Amazon Redshift writes all three logs (the user activity log only when it is in `logging.log_exports`), and the bucket's policy must let it write there; see [Bucket permissions for Amazon Redshift audit logging](https://docs.aws.amazon.com/redshift/latest/mgmt/db-auditing.html#db-auditing-bucket-permissions). The user activity log needs the `enable_user_activity_logging` parameter, which the module sets when the log is on.

### Alarms

The module creates five CloudWatch alarms: `health-critical` when the cluster reports itself unhealthy, `cpu-critical` and `cpu-warning` on CPU use, and `disk-critical` and `disk-warning` on the disk space used. They notify the topics `<name>-redshift-critical` and `<name>-redshift-warning`, which have no subscribers until you add some, for example with `aws_sns_topic_subscription` and `metadata.sns_topic["critical"].arn`. Each alarm also notifies its topic when it returns to normal. Set `alarms.enabled = false` to create none.

The topics are not encrypted unless you give `alarms.sns_kms_key_id`, a customer managed key whose policy lets `cloudwatch.amazonaws.com` use it, as the complete example's does. CloudWatch cannot publish to a topic encrypted with the AWS managed key `aws/sns`.

### Snapshots

Amazon Redshift takes automated snapshots about every 8 hours, or after every 5 GB of changes per node, and keeps them for `backup.retention_period` days. `backup.schedules` replaces that with your own schedule. Manual snapshots, which you take yourself, are kept for `backup.manual_snapshot_retention_period` days, or until you delete them.

- `s3_key_prefix` - (Optional) A prefix for the log files' keys in the bucket, such as `redshift/`.
- `retention_in_days` - (Optional) For `cloudwatch`: days to keep the logs. Defaults to `7`. One of `1`, `3`, `5`, `7`, `14`, `30`, `60`, `90`, `120`, `150`, `180`, `365`, `400`, `545`, `731`, `1096`, `1827`, `2192`, `2557`, `2922`, `3288` or `3653`, or `0` to keep them forever.
- `kms_key_id` - (Optional) For `cloudwatch`: ARN of a KMS key to encrypt the logs with. Its key policy must allow the CloudWatch Logs service in the cluster's Region. Without it, CloudWatch Logs encrypts them with a key it owns.

For `cloudwatch`, the module creates a log group for each log, `/aws/redshift/cluster/<name>/<log>`, before logging starts, so that the retention and key apply from the first line.

Type:

```hcl
object({
    destination       = optional(string)
    log_exports       = optional(set(string), ["connectionlog", "userlog", "useractivitylog"])
    bucket_name       = optional(string)
    s3_key_prefix     = optional(string)
    retention_in_days = optional(number, 7)
    kms_key_id        = optional(string)
  })
```

Default: `{}`

#### <a name="input_maintenance"></a> [maintenance](#input_maintenance)

Description: When and how AWS updates the cluster.

- `window` - (Optional) The weekly time range, in UTC, for maintenance, such as `sun:05:00-sun:05:30`. At least 30 minutes. Without it, AWS picks one.
- `allow_version_upgrade` - (Optional) Let AWS upgrade the cluster to new releases of the engine in the maintenance window. Defaults to `true`.
- `track_name` - (Optional) Which releases to follow: `current` for the newest, or `trailing` for the one before it. Defaults to `current`.

Type:

```hcl
object({
    window                = optional(string)
    allow_version_upgrade = optional(bool, true)
    track_name            = optional(string, "current")
  })
```

Default: `{}`

#### <a name="input_master_password"></a> [master_password](#input_master_password)

Description: The master user's password. Without it, the default, Amazon Redshift generates the password and keeps it in AWS Secrets Manager, and it is never stored in Terraform state; `metadata.redshift_cluster.master_password_secret_arn` gives the secret's ARN.

A password given here is stored in Terraform state in plain text. Use it only when the password must come from somewhere else. 8 to 64 printable ASCII characters, with at least one uppercase letter, one lowercase letter and one digit, and no `/`, `@`, `"`, `'`, `\` or spaces. Changing it, or setting it later, updates the cluster in place. Removing it again fails in Terraform alone; see [The master password](https://github.com/AutomateTheCloud/terraform-aws-redshift#the-master-password).

Type: `string`

Default: `null`

#### <a name="input_master_password_secret_kms_key_id"></a> [master_password_secret_kms_key_id](#input_master_password_secret_kms_key_id)

Description: ARN of a KMS key to encrypt the Secrets Manager secret that holds the master password. Without it, Secrets Manager uses the AWS managed key `aws/secretsmanager`. Not used with `master_password`.

Type: `string`

Default: `null`

#### <a name="input_master_username"></a> [master_username](#input_master_username)

Description: The name of the master user, the first database user, which can create other users. Defaults to `awsuser`. 1 to 128 lowercase letters, digits, underscores, plus signs, periods, at signs and hyphens, starting with a letter, and not `public`.

Used only when the cluster is created: changing it later does nothing. A cluster restored from a snapshot takes the master user from the snapshot.

Type: `string`

Default: `"awsuser"`

#### <a name="input_multi_az"></a> [multi_az](#input_multi_az)

Description: Run the cluster in two Availability Zones, with compute in each, so that it keeps working when one zone fails. Not for DC2 node types, and doubles the compute cost. The subnets in `subnet_ids` must cover at least two zones. Needs `availability_zone_relocation = false`. Defaults to `false`.

Type: `bool`

Default: `false`

#### <a name="input_number_of_nodes"></a> [number_of_nodes](#input_number_of_nodes)

Description: How many compute nodes the cluster has. `1` makes a single-node cluster; more make a multi-node cluster, which also has a leader node at no charge. Defaults to `1`. The most allowed depends on the node type. Changing it resizes the cluster in place.

Type: `number`

Default: `1`

#### <a name="input_parameter_group"></a> [parameter_group](#input_parameter_group)

Description: The cluster parameter group the module creates for the cluster, named `<name>-<family>`.

- `family` - (Optional) The parameter group family. Defaults to `redshift-2.0`.
- `parameters` - (Optional) Parameters to set, by name, such as `{ max_concurrency_scaling_clusters = "2" }`. Values are strings; give `wlm_json_configuration` as `jsonencode(...)`. Parameters left out keep the family's defaults.

The module sets `require_ssl` to `true`, so clients must connect with Transport Layer Security (TLS). Set it to `"false"` here only for clients that cannot. It also sets `enable_user_activity_logging`, to `true` when `logging` sends `useractivitylog`, and `false` otherwise. Some parameters take effect only after the cluster restarts.

Removing a parameter from `parameters` later does not reset it: AWS keeps the value, and every plan tries to remove it again. Set it to the family's default value instead (`aws redshift describe-default-cluster-parameters --parameter-group-family redshift-2.0` lists them).

Type:

```hcl
object({
    family     = optional(string, "redshift-2.0")
    parameters = optional(map(string), {})
  })
```

Default: `{}`

#### <a name="input_port"></a> [port](#input_port)

Description: The port clients connect to. Defaults to `5439`. From `5431` to `5455` or from `8191` to `8215`: AWS refuses other ports for every node type that uses managed storage, which are all the types it offers (RA3 and RG). Only the older DC2 types accepted `1150` to `65535`. Changing it updates the cluster in place and the security group's rules with it; the first plan afterwards shows only `metadata` changing, and applying it changes no resources.

Type: `number`

Default: `5439`

#### <a name="input_publicly_accessible"></a> [publicly_accessible](#input_publicly_accessible)

Description: Give the cluster a public IP address. Defaults to `false`. In subnets with a route to an internet gateway, anyone on the internet whom `security_group_ingress` allows can then reach it. Prefer a private connection, such as a VPN or AWS Systems Manager port forwarding through an instance in the VPC, or the Amazon Redshift Data API, which needs no network access to the cluster.

Type: `bool`

Default: `false`

#### <a name="input_region"></a> [region](#input_region)

Description: The AWS Region to create the cluster and everything else in, such as `us-west-2`. Defaults to the Region of the AWS provider passed to the module.

Type: `string`

Default: `null`

#### <a name="input_security_group_egress"></a> [security_group_egress](#input_security_group_egress)

Description: More destinations the cluster may connect to, besides Amazon S3 (see `allow_s3_egress`). The cluster needs no outbound rules to answer clients. Add an entry for a feature that makes the cluster connect out through the VPC, such as a federated query to an Amazon RDS database, or, with `enhanced_vpc_routing`, `COPY` from Amazon DynamoDB or an Amazon EMR cluster. The keys are names you choose; they only identify each rule.

Each entry takes:

- `port` - (Required) The TCP port to allow.

and exactly one of:

- `cidr_ipv4` - An IPv4 range, such as `10.0.0.0/16`.
- `cidr_ipv6` - An IPv6 range, such as `2001:db8::/56`.
- `security_group_id` - A security group whose members the cluster may connect to.
- `prefix_list_id` - A managed prefix list, such as the one for DynamoDB in the Region (`data.aws_ec2_managed_prefix_list` with name `com.amazonaws.<region>.dynamodb`).

and optionally:

- `description` - (Optional) What the destination is. Defaults to the key.

Type:

```hcl
map(object({
    port              = number
    cidr_ipv4         = optional(string)
    cidr_ipv6         = optional(string)
    security_group_id = optional(string)
    prefix_list_id    = optional(string)
    description       = optional(string)
  }))
```

Default: `{}`

#### <a name="input_security_group_ids"></a> [security_group_ids](#input_security_group_ids)

Description: IDs of more security groups to attach to the cluster, besides the one the module creates, such as a group shared by every data warehouse.

Type: `list(string)`

Default: `[]`

#### <a name="input_security_group_ingress"></a> [security_group_ingress](#input_security_group_ingress)

Description: Who can connect to the cluster. The module creates a security group for the cluster that allows the database port (`port`) over TCP from each source listed here, and from nothing else. With the default, `{}`, no client can connect. The keys are names you choose; they only identify each rule, so a security group created in the same configuration can be used.

Each source takes exactly one of:

- `cidr_ipv4` - An IPv4 range, such as `10.0.0.0/16`.
- `cidr_ipv6` - An IPv6 range, such as `2001:db8::/56`.
- `security_group_id` - A security group whose members may connect, such as the group of your application servers.
- `prefix_list_id` - A managed prefix list of ranges.

and optionally:

- `description` - (Optional) What the source is. Defaults to the key.

Type:

```hcl
map(object({
    cidr_ipv4         = optional(string)
    cidr_ipv6         = optional(string)
    security_group_id = optional(string)
    prefix_list_id    = optional(string)
    description       = optional(string)
  }))
```

Default: `{}`

#### <a name="input_skip_final_snapshot"></a> [skip_final_snapshot](#input_skip_final_snapshot)

Description: Delete the cluster without taking a final snapshot. Defaults to `false`: deleting the cluster first takes a snapshot named `<name>-final-<8 hex digits>`, which is kept until you delete it.

Type: `bool`

Default: `false`

#### <a name="input_snapshot_identifier"></a> [snapshot_identifier](#input_snapshot_identifier)

Description: The identifier of a snapshot to create the cluster from, such as a final snapshot of an earlier cluster. The node type and number of nodes may differ from the snapshot's, within what the snapshot's size allows. The master user and databases come from the snapshot, and the password is set as described in `master_password`.

Used only when the cluster is created: changing it later does nothing.

Type: `string`

Default: `null`

#### <a name="input_timeouts"></a> [timeouts](#input_timeouts)

Description: How long Terraform waits for the cluster to be created, updated or deleted, such as `120m`. Each defaults to `120m`.

Type:

```hcl
object({
    create = optional(string, "120m")
    update = optional(string, "120m")
    delete = optional(string, "120m")
  })
```

Default: `{}`

### Outputs

The following outputs are exported:

#### <a name="output_metadata"></a> [metadata](#output_metadata)

Description: Everything the module created, in one object, so that other configurations need only one reference:

- `details` - The scope, purpose and environment, each with its `name`, `abbr` (lowercase, words joined by underscores) and `machine` (lowercase letters and numbers only) forms, and the `tags` applied to every resource.
- `aws` - The `account.id`, and the `region` `name`, `abbr` (such as `use1` for `us-east-1`) and `description`.
- `redshift_cluster` - The cluster's `id`, `arn`, `endpoint` (`<dns_name>:<port>`), `dns_name`, `port`, `database_name`, `master_username`, `master_password_secret_arn` (the Secrets Manager secret, when Amazon Redshift keeps the password), `default_iam_role_arn`, `kms_key_id`, `cluster_namespace_arn` and the rest of its attributes. The nodes' addresses are left out, because they change with every resize; `aws redshift describe-clusters` lists them.
- `redshift_subnet_group` - The cluster subnet group, with its `name` and `subnet_ids`.
- `redshift_parameter_group` - The cluster parameter group, with its `name`, `family` and `parameter` values.
- `redshift_snapshot_schedule` - The snapshot schedule, with its `identifier` and `definitions`, or `null` without `backup.schedules`.
- `redshift_snapshot_schedule_association` - The schedule's attachment to the cluster, or `null`.
- `redshift_logging` - The audit logging settings, or `null` when `logging.destination` is not set.
- `iam_role` - The cluster's IAM role, with its `name` and `arn`.
- `iam_role_policy` - The role's inline policy from `iam_role.source_policy_documents`, or `null` when there are none.
- `iam_role_policy_attachment` - The managed policies attached to the role, keyed like `iam_role.managed_policy_arns`, or `null` when there are none.
- `security_group` - The cluster's security group, with its `id`, `arn` and `name`. Use its `id` as a source in other groups' rules.
- `vpc_security_group_ingress_rule` - The ingress rules, keyed like `security_group_ingress`, or `null` when there are none.
- `vpc_security_group_egress_rule` - The egress rules, keyed like `security_group_egress`, or `null` when there are none.
- `vpc_security_group_egress_rule_s3` - The egress rule to Amazon S3, or `null` when `allow_s3_egress` is `false`.
- `cloudwatch_log_group` - The audit log groups, keyed by log, each with its `name` and `arn`, or `null` when logs do not go to CloudWatch Logs.
- `sns_topic` - The alarm topics, keyed `critical` and `warning`, each with its `arn` and `name`, or `null` when `alarms.enabled` is `false`. Subscribe to them to receive the alarms.
- `sns_topic_policy` - The topics' access policies, keyed like `sns_topic`, or `null`.
- `cloudwatch_metric_alarm` - The alarms, keyed `health-critical`, `cpu-critical`, `cpu-warning`, `disk-critical` and `disk-warning`, each with its `alarm_name`, `arn` and `threshold`, or `null` when `alarms.enabled` is `false`.
